## 1. 需求理解摘要

- 业务目标：验证 Reward MVP 是否已从“有条件通过”推进到可电脑端验收状态，重点检查上轮 7 个关闭条件是否被产品界面、服务端规则和测试覆盖。
- 目标用户：内部验收人员、产品负责人、研发协作者；间接覆盖 parent、child、witness 三类业务角色。
- 核心场景：家长创建小约定，孩子完成猫咪番茄钟并提交复盘，家长兑现/延期/待复盘，系统生成亲子日记，同时保护证据照片、ChildNote、见证人权限和 AI/Kimi 边界。
- 主要能力：奖励禁用规则、证据照片隐私校验、待复盘中性文案校验、P08/P09/P10 页面文案与状态补齐、单元测试与构建验证。
- 范围：本轮只复审 `728de59 feat: align MVP with review gates` 后的实现，不重新扩展 MVP 范围。
- 预期结果：判断当前代码是否达到上轮评审要求，是否可进入电脑端验收，以及进入下一轮前必须修复的问题。

## 2. 评审结论

- 结论：有条件通过
- 需求类型：增量需求澄清 / 二次复审
- 输入物情况：PRD + 原型 + 修复后代码 + 验收调整记录

## 5. 风险提示

- 核心流程风险：P09 到 P10 的事务边界必须先修，否则一次中间失败就可能让家长回应页面和日记页面都无法恢复。
- 验收风险：当前 E2E 测试仍未启用，不能把“构建通过”直接等同于“产品闭环通过”。
- 权限风险：mock role switcher 已有 UI，但服务端 action 仍偏 seed demo 写法；见证人/孩子/家长越权提交路径需要真实拒绝测试。
- 规则风险：新增校验方向正确，但正则词库不是长期安全策略；后续至少要集中规则、补字段覆盖、补负向测试。

## 6. 通过前必须补齐项

进入“完全通过”前必须完成：

1. 修复 `submitParentResponse` 事务原子性，保证 Fulfillment、RepairCase、DiaryEntry、Contract 状态和 AuditLog 同步成功或同步回滚。
2. 启用 E2E 主链路测试，至少覆盖 fulfilled、delayed、pending_repair 和 witness 隐私不可见。
3. 扩展共享安全校验到 `promiseText` 和 `repairText`，移除英文-only 的重复校验路径。
4. server action 使用当前 mock actor 做权限校验，而不是只依赖 `seed_parent` / `seed_child`。

建议但不阻塞当前条件通过：

- 用 transition helper 收敛状态写入。
- 增加电脑端截图验收记录。
- 保持真实试点合规 gate。

## 7. 评审方最终结论

本轮复审结论为：有条件通过。

修复后的代码已经把上轮文档关闭条件中的关键规则推进到了实现层，并通过单元测试、类型检查和生产构建。当前可以继续做内部电脑端验收和下一轮修复，但不建议宣称“完整通过”。最优先的下一步是修复 P09 -> P10 的事务原子性，然后启用 E2E 主链路验收；完成这两项后，才适合再次申请“通过”级复审。
